# Smarthome

Система для создании "Умного дома". Поддерживает регистрацию и управление датчиками, снятия с них показаний, вызов команд и создание автоматических сценариев.

## Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут:
  - Подключить новый датчик к системе (только силами инженера платформы)
  - Узнать актуальный список подключенных датчиков и управлять им
  - Выполнить удаленную команду для датчика температуры
  
- Система поддерживает:
  - Интеграцию со сторонними датчиками по строгому синхронному протоколу

**Мониторинг температуры:**

- Пользователи могут:
  - Получить моментальные показатели температуры любого датчика
- Система поддерживает:
  - Синхронный опрос всех датчиков в системе

### 2. Анализ архитектуры монолитного приложения

При реализации текущего решения были выбраны следующие технологии:

- Язык программирования Golang 1.22 + web-фреймворк Gin
- PostgreSQL 16

Решение реализовано как единый монолитный сервис.
Сервис интегрирован с зарегистрированными в нем датчиками по стандартному синхронному протоколу, изменения датчика получаются при прямом запросе клиента.

### 3. Определение доменов и границы контекстов

Существует два основных домена приложения, которые подразделяются на поддомены:

- Управление устройствами
  - Управление датчиками - регистрация и управление списком, отправка команд, выполнение сценариев
  - Управление показаниями - сбор переданных показаний и их отображение
- Управление пользователями - регистрация и авторизация пользователей приложения

### **4. Проблемы монолитного решения**

- Отдельные компоненты сервиса имеют иные требования к ресурсам, чем другие, например функционал выполнения сценариев намного менее загруженный, чем функционал управления датчиками, поэтому его нет смысла масштабировать совместно
- Текущая база данных не подходит для сбора временной аналитики на масштабе регионов - она будет неэффективна по хранению и исполнению при большом объеме статистических данных
- Текущий метод опроса датчика не масштабируется - датчики опрашиваются по единому поллинг протоколу, который:
  - Не масштабируется от количества датчиков (нет протокола координации опросов)
  - Не работает за NAT
  - Не позволяет получать обновления в реальном времени
  - Не может стать стандартным для поставщиков оборудования
  - При отказе сервиса не существует контура, который может собрать показания - исторические данные окажутся утеряны
- Выполнение удаленных операций не надежно и не следует семантике exactly-once или идемпотентности, что критично для датчиков
- Не существует механизма сериализации вызовов к датчику - возможны race-condition при опросах

# Задание 4. Создание и документирование API

### 1. Тип API

Для синхронного взаимодействия микросервисов (отправка команд устройствам и чтение их статусов) выбран gRPC:

- контракты хранятся в одном месте (`schemas/api/`), из них кодогенерацией получаются клиенты и серверы для всех сервисов — все участники полагаются на единый источник истины;
- gRPC нативно поддерживает серверный стриминг поверх HTTP/2 — это путь эволюции: поллинг статуса команды в будущем заменяется на подписку без смены протокола.

Событийные потоки телеметрии передаются асинхронно через брокер сообщений (Kafka) и документируются AsyncAPI. Внешний (клиентский) API монолита остаётся REST и документируется OpenAPI.

### 2. Документация API

- [OpenAPI: API умного дома (монолит)](schemas/api/smarthome_api_spec.yaml)
- [OpenAPI: API сценариев](schemas/api/scenarios_api_spec.yaml)
- [AsyncAPI: события датчиков (телеметрия)](schemas/api/sensors_interactions_spec.yaml)
- [gRPC/protobuf: сервис удалённого управления устройствами](schemas/api/remote_device_control_service_spec.proto)

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
